GigsForGigs - Client-Side Workflow and REST API Mapping
========================================================

Scope
- Derived from front-end HTML/JS modules in /front-end.
- Focused on client, manager, gig, and admin workflows.
- Maps client-side actions to REST endpoints using POST, GET, PUT, DELETE (and PATCH for partial updates).

Pages and Roles (Frontend)
- Public: login.html, signup.html, role-selection.html
- Client: client-dashboard.html, post-gig.html, search-talent.html, my-gigs-client.html, review-shortlist.html,
  review-deliverables.html, client-profile-selection.html, add-manager.html, add-manager-flow.html,
  profile-completion-client.html
- Manager: manager-dashboard.html (views client contracts), manager-invite-setup.html (public setup link)
- Gig: gig-dashboard.html, explore-tasks.html, pending-requests.html, active-tasks.html, completed-projects.html,
  project-detail.html, post-service.html, submit-deliverables.html, gig-profile.html,
  profile-completion-gig.html, total-earnings.html
- Admin (separate auth): /front-end/js/admin/* + admin pages (clients, projects, reviews, etc.)

Core Data Entities (from frontend modules)
- Users (client, manager, gig) and Auth
- Client profile, Gig profile
- Tasks (client posts, gig accepts; statuses: open, in_progress, under_review, completed)
- Applications (gig applies to task; statuses: pending, shortlisted, rejected)
- Services (gig posts service; client hires -> request)
- Hire Requests / Gig Requests (client requests service; gig accepts/declines)
- Contracts (client sees active/pending/completed from gigState)
- Deliverables (gig submits; client approves/revision)
- Payments (release on approval, represented in UI)
- Reviews (not fully wired in front-end, but admin dashboard includes review data)
- Manager invites (client invites manager, manager completes setup)

Client-Side Workflow Summary
1) Auth + Onboarding
- Signup and login by role (client, manager, gig).
- First-time users complete profile (client or gig).
- Manager invite flow: client creates invite; manager completes setup via invite link.

2) Client Flow
- Post a task (post-gig.html) -> creates Task (status open).
- View dashboard (client-dashboard.html) -> sees posted tasks and contract activity.
- Review shortlist (review-shortlist.html) -> shortlist or reject applications.
- Approve & hire -> assigns gig to task (status in_progress) and rejects other applications.
- Active contracts (my-gigs-client.html) -> view contract, review deliverables.
- Review deliverables (review-deliverables.html) -> approve or request revision; on approve, task completed.
- Search talent (search-talent.html) -> view services, send hire request.

3) Manager Flow
- Same contracts view as client (my-gigs-client.html) but no payment approval.
- Can view shortlist and contracts (read-only or limited actions).

4) Gig Professional Flow
- Explore tasks (explore-tasks.html) -> view open tasks.
- Apply to tasks -> creates Application (pending).
- Pending requests (pending-requests.html) -> accept/decline hire requests.
- Active tasks (active-tasks.html) -> view assigned tasks.
- Project detail -> submit deliverable.
- Completed projects -> view completed tasks.
- Post service (post-service.html) -> create Service used in talent search.

5) Admin Flow (separate auth)
- Admin login via adminAuth (admin123@gmail.com).
- CRUD on clients, managers, professionals, projects, reviews, payments, reports, categories.

Suggested REST Endpoints (by Entity)

AUTH
- POST /api/auth/login
- POST /api/auth/signup
- POST /api/auth/logout
- GET  /api/auth/session

USERS
- GET  /api/users (admin or super-admin)
- GET  /api/users/{userId}
- PUT  /api/users/{userId} (update profile fields, role metadata)
- PATCH /api/users/{userId} (partial updates)
- DELETE /api/users/{userId} (soft delete)

CLIENT PROFILE
- GET  /api/clients/{clientId}/profile
- POST /api/clients/{clientId}/profile (initial create)
- PUT  /api/clients/{clientId}/profile (update full)
- PATCH /api/clients/{clientId}/profile (partial)

GIG PROFILE
- GET  /api/gigs/{gigId}/profile
- POST /api/gigs/{gigId}/profile
- PUT  /api/gigs/{gigId}/profile
- PATCH /api/gigs/{gigId}/profile

TASKS (client posts)
- GET  /api/tasks (filters: status, category, clientId, search)
- GET  /api/tasks/{taskId}
- POST /api/tasks (create task)
- PUT  /api/tasks/{taskId} (edit task)
- PATCH /api/tasks/{taskId} (partial update: status, assignedTo)
- DELETE /api/tasks/{taskId}

APPLICATIONS (gig applies to task)
- GET  /api/applications (filters: taskId, gigId, status)
- GET  /api/applications/{applicationId}
- POST /api/tasks/{taskId}/applications (apply)
- PUT  /api/applications/{applicationId} (shortlist/reject)
- PATCH /api/applications/{applicationId} (status updates)
- DELETE /api/applications/{applicationId}

SERVICES (gig posts service)
- GET  /api/services (filters: category, skill, rate, rating)
- GET  /api/services/{serviceId}
- POST /api/services (create service)
- PUT  /api/services/{serviceId} (update)
- PATCH /api/services/{serviceId}
- DELETE /api/services/{serviceId}

HIRE REQUESTS (client hires from service)
- GET  /api/requests (filters: clientId, gigId, status)
- GET  /api/requests/{requestId}
- POST /api/services/{serviceId}/requests (create hire request)
- PUT  /api/requests/{requestId} (accept/decline)
- PATCH /api/requests/{requestId} (status updates)
- DELETE /api/requests/{requestId}

CONTRACTS (client/gig active view)
- GET  /api/contracts (filters: clientId, gigId, status)
- GET  /api/contracts/{contractId}
- POST /api/contracts (create from accepted request or hire)
- PUT  /api/contracts/{contractId}
- PATCH /api/contracts/{contractId} (progress, status)
- DELETE /api/contracts/{contractId}

DELIVERABLES
- GET  /api/tasks/{taskId}/deliverables
- GET  /api/deliverables/{deliverableId}
- POST /api/tasks/{taskId}/deliverables (submit)
- PUT  /api/deliverables/{deliverableId} (update content)
- PATCH /api/deliverables/{deliverableId} (status: approved, revision_requested)
- DELETE /api/deliverables/{deliverableId}

PAYMENTS (implicit in client approval flow)
- GET  /api/payments (filters: taskId, gigId, clientId)
- GET  /api/payments/{paymentId}
- POST /api/payments (release payment for approved deliverable)
- PUT  /api/payments/{paymentId} (update status)
- PATCH /api/payments/{paymentId}
- DELETE /api/payments/{paymentId}

REVIEWS
- GET  /api/reviews (filters: reviewerId, revieweeId, status)
- GET  /api/reviews/{reviewId}
- POST /api/reviews (create review)
- PUT  /api/reviews/{reviewId}
- PATCH /api/reviews/{reviewId} (status: verified/reported)
- DELETE /api/reviews/{reviewId}

MANAGER INVITES
- GET  /api/manager-invites (filters: clientId, email, status)
- GET  /api/manager-invites/{inviteId}
- POST /api/manager-invites (create invite)
- PUT  /api/manager-invites/{inviteId} (accept)
- PATCH /api/manager-invites/{inviteId}
- DELETE /api/manager-invites/{inviteId}

ADMIN (separate auth namespace)
- POST /api/admin/auth/login
- GET  /api/admin/users (admins)
- CRUD: /api/admin/clients, /api/admin/managers, /api/admin/professionals,
  /api/admin/projects, /api/admin/reviews, /api/admin/payments, /api/admin/reports,
  /api/admin/categories

Notes on Status Transitions (client-side behavior)
- Task: open -> in_progress (assigned) -> under_review (deliverable submitted) -> completed
- Application: pending -> shortlisted (client action) -> rejected (client action)
- Hire Request: pending -> accepted/declined (gig action)
- Deliverable: submitted -> approved or revision_requested
- Contract: pending -> active -> completed
